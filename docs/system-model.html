Nabe architecture note

System model

This document explains how Nabe should work when it grows beyond the current MVP: identity, group permissions, central and edge DNS engines, query visibility, aggregated stats, audit logs, and secrets. The canonical decision records live in docs/adr/.

Core answer Central is the control plane and dashboard, not the universal raw log bucket. Edges keep raw DNS logs locally by default. Interactive log views use a live edge session, not slow polling jobs. Central stores policy, identity, audit events, health, inventory, and rollups.

Design Principles

1. Nabe owns authorization

Zitadel proves identity. Nabe decides product access. External roles can seed memberships, but final permission checks happen in Nabe against Nabe resources.

OIDCRBACTenant scope

2. DNS engines are adapters

AdGuard Home resolves DNS and provides engine APIs. Nabe translates product concepts like Device Clients and policies into engine config.

AdGuardUnboundAdapter

3. Logs stay local unless needed

Raw DNS query logs are sensitive browsing metadata. By default they stay on the engine that observed them. Central receives rollups and can request filtered windows over a live edge channel when a permission allows it.

PrivacyShort TTLFiltered

4. Every action is auditable

Control-plane actions are different from DNS query logs. Audit events belong centrally because they explain who changed policy, enrolled an edge, viewed logs, or used break-glass access.

AuditAppend-only

5. Edges connect outbound

Speiche should maintain outbound connectivity to central. Central keeps an open session for interactive reads and receives background jobs for slower work.

No inbound edge APIJobs

6. Break-glass is not product UX

Native AdGuard UI is useful for recovery, but it cannot enforce Nabe ownership, role checks, audit policy, or log filtering. It must remain private and separately audited.

Private UIEmergency only

System Shape

The clean mental model is three planes: identity plane, control plane, and DNS/data plane. Central coordinates them, but only the DNS engines answer DNS queries.
UserSigns in with Zitadel. Uses Nabe Console or CLI.
Nabe APIChecks session, role, tenant, ownership, and resource scope.
Nabe DBStores subjects, tenants, roles, devices, policies, edges, jobs, audits.
Engine adapterApplies desired state to central AdGuard or edge job target.
DNS engineAdGuard Home plus Unbound resolve, block, count, and log locally.

Who Owns What

Central Nabe owns

  • Subjects, tenants, memberships, roles, and permissions.
  • Device Clients, ClientID tokens, and ownership metadata.
  • Desired DNS policy and policy assignment.
  • Edge inventory, online status, and job results.
  • Audit events for control actions and log access.
  • Aggregated stats that are safe to store centrally.

Each DNS engine owns locally

  • Actual DNS request handling.
  • Raw query log source data.
  • Engine-local counters and cache state.
  • Resolver config, bind addresses, and local health.
  • Break-glass UI/API, hidden behind private access.
  • Emergency operation if central is temporarily unavailable.

Permission System

Use RBAC for manageability, but do not stop at roles. Every decision should include role permissions, resource scope, tenant membership, ownership, and constraints. This avoids the common problem where a group admin accidentally becomes a platform admin or can read unrelated logs.

Role Scope Can do Cannot do
platform_admin Whole installation Manage engines, edges, tenants, global settings, secrets, break-glass. Bypass audit. Read raw tenant logs without a logged reason.
platform_operator Whole installation Read health, restart jobs, inspect failures, apply system updates. Read tenant query logs or manage tenant members by default.
tenant_owner One tenant or family group Manage tenant members, tenant policies, tenant devices, tenant edge assignment. Manage central secrets or other tenants.
tenant_admin One tenant Manage devices and policies, view tenant stats, request tenant log views. Delete tenant, change billing/system ownership, break-glass native UI.
tenant_viewer One tenant Read device and policy configuration, view aggregated tenant stats. Change policy or view raw query logs.
user Self plus assigned tenant Manage own Device Clients, see own device status, maybe own logs. See other users' raw logs or tenant-wide settings.
restricted_user Self Use DNS service and see basic device status. View query logs, change policy, create new tokens.

Practical rule: roles grant capabilities, but resource ownership decides which rows and which DNS records are visible. A tenant admin may have querylog.read_tenant, but only for that tenant's client ids and only for an allowed time window.

The safe architecture is not "ship every DNS query to central". Nabe should use tiers of telemetry with different privacy and retention rules.

Raw query log access flow
  1. User requests logs for a device, tenant, edge, and time window.
  2. Nabe checks querylog.read_own or querylog.read_tenant.
  3. Nabe writes an audit event before the query is served.
  4. Central AdGuard adapter queries central AdGuard directly, or Nabe sends a live query over the active Speiche session for an edge.
  5. Engine-side filtering should restrict by ClientID/IP and time window when possible.
  6. Nabe re-filters results by owned Device Client IDs before returning.
  7. Response is streamed or cached briefly, not stored as a permanent central log.
Interactive logs must not use polling jobs

Clicking "show DNS queries" should feel like opening the native AdGuard query panel. A background job loop that waits for Speiche to poll every X seconds is acceptable for upgrades, policy application, rollup collection, and maintenance, but it is not acceptable for interactive log browsing.

Use caseTransportExpected UXCentral storage
Open recent query log Browser -> Nabe API stream -> active Speiche session -> local AdGuard API First page starts quickly, then paginates or streams No permanent raw storage
Tail live queries Browser WebSocket/SSE to Nabe API, multiplexed over Speiche session Near-real-time rows while the edge is online Optional short memory cache only
Apply policy or client config Durable edge job with result reporting Progress state, retry-safe Job and result stored
Collect hourly stats Scheduled background job or Speiche push Not interactive Aggregated buckets stored

This keeps the one-dashboard experience while avoiding a central database full of raw browsing history. The dashboard is unified; the data source is federated.

Application logging pattern

Nabe services should emit one structured wide event per request or job completion. Include request id, subject id, tenant id, resource ids, permission decision, outcome, duration, version, and edge id. Do not log tokens, passwords, AdGuard credentials, full DNS query payloads, session cookies, or private keys.

Security Model

Identity and sessions

Users authenticate with Zitadel through OIDC. Nabe validates the session and maps the external subject to an internal subject. Zitadel role claims can bootstrap global role and tenant group assignment, but Nabe stores the effective product authorization state.

Device tokens

ClientID values are secret-like identifiers for encrypted DNS clients. Show them once, hash for lookup where possible, encrypt if they must be replayed into an engine, and support rotation.

Engine credentials

AdGuard API credentials stay server-side. The browser receives only Nabe data. Edge credentials stay on the edge and are used by Speiche or local adapters.

Edge trust

Enrollment token should be exchanged for a durable node identity. After enrollment, prefer mTLS or signed node tokens, short-lived job leases, replay protection, and per-node revocation.

Network boundary

Edge nodes connect outbound. Native AdGuard UI binds loopback by default. If exposed for recovery, access must be explicit, private, time-limited, and audited.

Central compromise limit

Central should not contain every household's raw DNS history. A central breach should expose policy, metadata, and rollups, not the full browsing log of every edge.

Do not multi-tenant a physical edge for real users until client identity is reliable. If a home router forwards all DNS as one IP, per-user log permissions cannot be enforced accurately. Use DHCP, ClientID encrypted DNS, or another reliable client identity source first.

End-State Flows

Create a group and assign admins

Platform admin creates a tenant. Zitadel group or role claim maps users into that tenant. Nabe assigns tenant_owner, tenant_admin, tenant_viewer, or user. All future reads and writes are tenant-scoped.

Enroll an edge AdGuard

Admin creates an edge enrollment. Pi runs Nabe CLI. Speiche enrolls, stores identity locally, reports heartbeat and inventory, receives jobs, and applies Nabe desired state to local AdGuard.

Manage a Device Client

User or tenant admin creates a device. Nabe creates a Device Client and ClientID token, assigns policy, writes audit, and applies a persistent/allowed client to the chosen DNS engine.

View stats without centralizing logs

Edge sends aggregate counters. User sees own or tenant rollups based on stats.read_*. Raw domains stay local unless a permitted, audited query-log view is requested.

Open edge query logs instantly

Browser opens a Nabe API stream. Nabe authorizes the request, creates a short-lived query capability containing edge id, client ids, time window, and row limit, then sends it over the active Speiche session. Speiche queries local AdGuard, filters results, and streams rows back through Nabe. No polling delay is required.

IT/OT Security Review

Treat Speiche as a conduit between zones, not as a convenience agent. Even in a home or homelab, DNS can become operational infrastructure. In an OT-style network, central must never gain unrestricted remote administration over the edge zone just because the edge is connected.
Security question Risk Required control Design decision
Can central run arbitrary commands on an edge? Central compromise becomes edge compromise. Command allowlist, typed jobs, no remote shell by default, per-command authorization. Speiche accepts only protocol-defined operations such as health, read scoped logs, apply policy, rotate token, restart known service.
Can an edge impersonate another edge? Cross-tenant data exposure or forged telemetry. Enrollment exchange, durable node identity, mTLS or signed node token, revocation. Enrollment token is single-use or short-lived. Runtime identity is separate and revocable.
Can a tenant admin read another tenant's DNS history? High privacy breach. Tenant scope, Device Client ownership, server-side filtering, audit on every raw log view. Logs are filtered by allowed client ids and time window before display. Weak attribution disables per-user log views.
What if an edge is offline? Operator expects logs, but raw data is unavailable. Clear degraded state, last-seen time, local retention, optional encrypted recent cache. Default: no offline raw logs. Optional: short central cache with explicit tenant consent and retention.
Can policy changes break operational DNS? Loss of name resolution can disrupt IT and OT workflows. Staged config, validation, rollback, maintenance windows, emergency local fallback. Policy apply is a durable job with preflight, versioned desired state, result, and rollback target.
Can native AdGuard UI bypass Nabe controls? Untracked policy/log access and privilege drift. Private bind, break-glass reason, separate credentials, audit, periodic drift detection. Native UI remains loopback/private and is not normal product UX.
Is the installer a supply-chain risk? curl | bash can install attacker-controlled code if transport or source is compromised. Signed releases, checksums, pinned source, least-privilege installer, reproducible build path. Developer bootstrap may use source install; production edge install needs signed artifacts.
Can telemetry leak secrets? Logs and traces may expose tokens, DNS queries, cookies, or credentials. Structured allowlisted fields, redaction tests, no secrets in logs, separate raw query path. Wide events are allowed for control-plane operations, not raw DNS payload dumping.

Controls that should be mandatory before real multi-tenant use
  • Deny-by-default authorization middleware on every API route.
  • Stable tenant and Device Client ownership model with tests for cross-tenant denial.
  • Signed edge identity, revocation, and enrollment-token rotation.
  • Typed Speiche command protocol with no arbitrary shell execution.
  • Per-command audit events, including raw query-log views and break-glass access.
  • Config versioning, preflight validation, apply result, and rollback for DNS changes.
  • Explicit raw-log retention policy for each tenant and edge.
  • Secret storage strategy for engine credentials and token material.
  • Drift detection between Nabe desired state and AdGuard actual state.
  • Backups and restore tests for central DB and edge identity/config.
OT-specific constraints if this ever touches real operational networks
  • No active discovery or scanning by default. Inventory should be declared or passively observed.
  • No automatic policy changes during operational windows unless explicitly approved.
  • No dependency on public cloud for local DNS continuity once policy is applied.
  • Local fallback must keep DNS service running if central is down.
  • Changes must be attributable, reviewable, and reversible.
  • Separate safety/operations approval for DHCP, resolver, or network-wide DNS cutovers.

Recommended Documentation And Implementation Rollout

Phase 1 Document this model in Markdown too, then align database table names with it: tenants, memberships, roles, permissions, edges, device_clients, policies, audit_events, telemetry_rollups.
Phase 2 Implement permission middleware in Nabe API. Every handler declares action and resource loader. Tests cover deny by default, tenant isolation, and owner-only visibility.
Phase 3 Implement edge job protocol for desired state: apply clients, apply policy, collect rollup, fetch scoped query log window.
Phase 4 Implement telemetry retention settings per tenant and edge. Make raw log central caching opt-in, short-lived, and audited.
